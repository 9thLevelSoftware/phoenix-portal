# Exercise Catalog & ID-First Resolution — Portal

**Date:** 2026-05-03
**Status:** Approved
**Resolves:** [GitHub Issue #404](https://github.com/9thLevelSoftware/Project-Phoenix-MP/issues/404)
**Scope:** phoenix-portal (Supabase migrations, Edge Functions, React UI)
**Companion Spec:** `Project-Phoenix-MP/docs/superpowers/specs/2026-05-03-exercise-catalog-mobile.md`

## Problem

Exercises with identical names but different equipment variants (e.g., "Bicep Curl" with Handles vs Long Bar vs Short Bar) lose their identity during the sync round-trip between mobile and portal. The portal stores exercises by name string only — no exercise catalog, no stable IDs. When the mobile pulls data back, a `LIMIT 1` name lookup returns an arbitrary variant, corrupting routines.

### Portal-Side Root Causes

1. No master exercise catalog in Supabase — only per-session exercise rows
2. `routine_exercises`, `exercise_progress`, `personal_records`, `overload_suggestions`, `user_goals` all identify exercises by name string only
3. The sync push edge function discards the mobile's `exerciseId` and stores only `name` + `muscle_group`
4. The sync pull edge function returns name-only data, losing exercise identity
5. The portal's exercise library is a 32-entry static array (`exercise-library.ts`) with just `{name, muscleGroup}`

### Impact

- Routines corrupted on sync round-trip (wrong equipment variant assigned)
- Analytics for identically-named exercises merged or randomly split
- Portal users can't distinguish equipment variants when creating routines
- Personal records may be attributed to the wrong exercise variant

## Solution

A shared exercise catalog in Supabase that both apps reference by stable ID, with equipment-variant display names for human clarity.

## Data Source

Exercise data is sourced from the [Exercise Library](https://github.com/exerciselibrary/exerciselibrary.github.io) repository, originally ripped from the official Vitruvian Trainer app. The `exercise_dump.json` file contains 1,176 exercises with stable IDs, videos, muscle groups, equipment arrays, and metadata.

The mobile app already imports this file and uses the JSON's `id` field as its SQLite primary key. These same IDs become the canonical `exercise_catalog.id` in Supabase.

## Shared Integration Contract

This section is duplicated in the mobile companion spec. Both sides must agree on these definitions.

### Exercise Catalog ID Scheme

- Library exercises: Stable IDs from `exercise_dump.json` (e.g., `"4kmhj9yyZcBI54Vi"`)
- Custom exercises: `"custom_<timestamp>"` format (generated by mobile)
- ID type: `TEXT` (not UUID)

### Sync DTO Shape (Push — Mobile to Supabase)

```typescript
// Session exercises
interface ExerciseSyncDto {
  id: string;               // Session-exercise instance UUID
  sessionId: string;
  exerciseId?: string;       // NEW: exercise_catalog.id
  name: string;              // Base name (fallback)
  muscleGroup: string;
  orderIndex: number;
  sets: SetSyncDto[];
}

// Routine exercises
interface RoutineExerciseSyncDto {
  id: string;                // Routine-exercise instance UUID
  routineId: string;
  exerciseId?: string;       // NEW: exercise_catalog.id
  exerciseName: string;      // Base name (fallback)
  displayName?: string;      // NEW: disambiguated name
  exerciseMuscleGroup: string;
  exerciseEquipment?: string; // NEW: equipment snapshot (comma-separated)
  // ... remaining fields unchanged
}

// Custom exercises
interface CustomExerciseSyncDto {
  clientId: string;          // "custom_<timestamp>"
  serverId?: string;
  name: string;
  muscleGroup: string;
  equipment: string;
  defaultCableConfig: string;
  displayName?: string;      // NEW
  // ... remaining fields unchanged
}
```

### Sync DTO Shape (Pull — Supabase to Mobile)

Same DTO shapes as push, with the addition of:
- `exerciseId` populated from `routine_exercises.exercise_id` FK
- `displayName` populated from `exercise_catalog.display_name` (joined)
- `exerciseEquipment` populated from `exercise_catalog.equipment` (joined)

### Equipment Display Labels

| Code | Display |
|------|---------|
| HANDLES | Handles |
| BAR | Bar |
| LONG_BAR | Long Bar |
| SHORT_BAR | Short Bar |
| ROPE | Rope |
| BELT | Belt |
| BENCH | Bench |
| STRAPS | Straps |
| GREY_CABLES | Cables |

### Display Name Generation Rule

```
If only one exercise has this base name -> display_name = name
If multiple exercises share the base name -> display_name = "{name} ({primary equipment})"

"Primary equipment" = first item in the equipment array. The exercise_dump.json
consistently lists the most distinctive attachment first (e.g., ["LONG_BAR", "BENCH"]
-> "Long Bar" is primary). If the equipment array is empty, fall back to display_name = name.
```

## 1. Exercise Catalog Table (Supabase Migration)

### Schema

```sql
CREATE TABLE exercise_catalog (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    display_name TEXT NOT NULL,
    description TEXT,
    muscle_group TEXT NOT NULL,
    muscle_groups TEXT[] NOT NULL DEFAULT '{}',
    muscles TEXT[] DEFAULT '{}',
    equipment TEXT[] NOT NULL DEFAULT '{}',
    movement TEXT,
    sidedness TEXT,
    grip TEXT,
    grip_width TEXT,
    default_cable_config TEXT NOT NULL DEFAULT 'DOUBLE',
    min_rep_range REAL,
    popularity REAL NOT NULL DEFAULT 0,
    aliases TEXT[] DEFAULT '{}',
    thumbnail_url TEXT,
    archived BOOLEAN NOT NULL DEFAULT FALSE,
    is_custom BOOLEAN NOT NULL DEFAULT FALSE,
    user_id UUID REFERENCES auth.users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

ALTER TABLE exercise_catalog ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Library exercises visible to all authenticated users"
    ON exercise_catalog FOR SELECT
    USING (is_custom = FALSE OR user_id = auth.uid());

CREATE POLICY "Users can manage their own custom exercises"
    ON exercise_catalog FOR ALL
    USING (is_custom = TRUE AND user_id = auth.uid());
```

### Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| ID source | Reuse mobile's existing IDs from exercise_dump.json | Stable across all installations, no new scheme needed |
| Custom exercises | Same table with `is_custom` flag + `user_id` | Single FK target, RLS handles visibility |
| `display_name` vs `name` | Separate columns | `name` = base name for grouping/search; `display_name` = disambiguated for UI |
| Arrays vs comma-separated | PostgreSQL `TEXT[]` arrays | Native indexing, containment queries (`@>`) |
| Videos | `thumbnail_url` only | Full video support is a separate feature |

### Indexes

```sql
CREATE INDEX idx_exercise_catalog_name ON exercise_catalog(LOWER(name));
CREATE INDEX idx_exercise_catalog_muscle ON exercise_catalog(muscle_group);
CREATE INDEX idx_exercise_catalog_movement ON exercise_catalog(movement);
```

### Seeding

A seed script (run as part of the migration or as a separate follow-up migration) parses `exercise_dump.json` and inserts all 1,176 library exercises with:
- IDs from the JSON's `id` field
- `display_name` generated per the disambiguation rule above
- `equipment` parsed from JSON arrays into PostgreSQL arrays
- `muscle_groups` and `muscles` parsed similarly
- `thumbnail_url` extracted from the first video entry's thumbnail field
- `is_custom = false`, `user_id = NULL` for all library exercises

## 2. FK Additions & Data Migration

### New Columns

| Table | New Column | Nullable | Notes |
|-------|-----------|----------|-------|
| `routine_exercises` | `exercise_id TEXT REFERENCES exercise_catalog(id)` | Yes | Portal-created routines populate immediately |
| `exercises` (session) | `exercise_id TEXT REFERENCES exercise_catalog(id)` | Yes | Mobile sync populates going forward |
| `exercise_progress` | `exercise_id TEXT REFERENCES exercise_catalog(id)` | Yes | Analytics keyed on ID |
| `personal_records` | `exercise_id TEXT REFERENCES exercise_catalog(id)` | Yes | PRs linked to canonical exercise |
| `overload_suggestions` | `exercise_id TEXT REFERENCES exercise_catalog(id)` | Yes | Suggestions linked to canonical exercise |
| `user_goals` | `exercise_id TEXT REFERENCES exercise_catalog(id)` | Yes | Goals linked to canonical exercise |

### Backfill Strategy

```sql
-- Phase 1: Unambiguous matches (name appears exactly once in catalog)
UPDATE routine_exercises re
SET exercise_id = ec.id
FROM exercise_catalog ec
WHERE LOWER(TRIM(re.name)) = LOWER(TRIM(ec.name))
AND LOWER(TRIM(ec.name)) IN (
    SELECT LOWER(TRIM(name)) FROM exercise_catalog
    GROUP BY LOWER(TRIM(name)) HAVING COUNT(*) = 1
);

-- Repeat pattern for: exercises, exercise_progress, personal_records,
-- overload_suggestions, user_goals (matching on exercise_name column)

-- Phase 2: Ambiguous matches left NULL
-- Future syncs will progressively fill these in
```

### Transition Rules

- `exercise_name`/`name` columns are **NOT removed** — they stay as denormalized display fallbacks permanently
- All new writes populate `exercise_id`
- Reads prefer `exercise_id` (join to catalog for display), fall back to raw name if NULL
- NULLs fill in naturally as users sync new workouts and create new routines

### Indexes

```sql
CREATE INDEX idx_routine_exercises_exercise_id ON routine_exercises(exercise_id);
CREATE INDEX idx_exercises_exercise_id ON exercises(exercise_id);
CREATE INDEX idx_exercise_progress_exercise_id ON exercise_progress(exercise_id);
CREATE INDEX idx_personal_records_exercise_id ON personal_records(exercise_id);
```

## 3. Edge Function Changes

### Sync Push (`mobile-sync-push/index.ts`)

**Current behavior:** Ignores mobile's `exerciseId`, generates new UUIDs for session exercises, stores only `name` + `muscle_group`.

**New behavior:**

Session exercises:
1. Read `exerciseId` from the DTO payload
2. If provided, validate it exists in `exercise_catalog`
3. Insert into `exercises` table WITH `exercise_id` FK
4. Insert into `exercise_progress` WITH `exercise_id` FK
5. Upsert `personal_records` WITH `exercise_id` FK

Routine exercises:
1. Read `exerciseId` from the DTO payload
2. Upsert `routine_exercises` WITH `exercise_id` FK
3. Store `exerciseName` and `exerciseEquipment` as denormalized fallbacks

Custom exercises:
1. Read `CustomExerciseSyncDto` from push payload (already exists today)
2. UPSERT into `exercise_catalog` with `is_custom = true`, `user_id = auth.uid()`
3. Custom exercise ID is now valid for FK references in routines/sessions

**Backward compatibility:** `exerciseId` is optional in all DTOs. Old mobile versions that don't send it produce NULL `exercise_id` values — same as today, no regression.

### Sync Pull (`mobile-sync-pull/index.ts`)

**Current behavior:** Returns routines with exercise name + muscle group only.

**New behavior:**
1. JOIN `routine_exercises` to `exercise_catalog` on `exercise_id`
2. Return `exercise_id`, `display_name`, and `equipment` from the catalog
3. Return custom exercises from `exercise_catalog WHERE is_custom = true AND user_id = auth.uid()`
4. Fall back to name-only fields if `exercise_id` is NULL (legacy data)

**Backward compatibility:** New fields are additive. Old mobile versions ignore fields they don't recognize.

### Bug Fix Path (Issue #404)

Before:
```
Mobile: Routine -> "Bicep Curl" (exerciseId: "abc123", equipment: LONG_BAR)
  -> push
Portal DB: routine_exercises -> name: "Bicep Curl" (exercise_id: NULL)
  -> pull
Mobile: findExerciseByName("Bicep Curl") LIMIT 1 -> returns SHORT_BAR variant (WRONG)
```

After:
```
Mobile: Routine -> "Bicep Curl" (exerciseId: "abc123", equipment: LONG_BAR)
  -> push
Portal DB: routine_exercises -> name: "Bicep Curl", exercise_id: "abc123"
  -> pull
Mobile: getExerciseById("abc123") -> returns LONG_BAR variant (CORRECT)
```

## 4. Portal UI Changes

### Exercise Selection (RoutineBuilder)

**Current:** Merges user's past workout history with 32-entry static array. Deduplicates by `name.toLowerCase()`.

**New:**
- Exercise source: `exercise_catalog` table (1,176+ library + user's custom exercises)
- Each exercise shows `display_name` with equipment variant
- Equipment shown as tag/badge (matching mobile UI: "Arms - Long Bar")
- Muscle group filtering against proper array data
- Search hits `name`, `display_name`, `aliases`, `muscles`
- `exercise-library.ts` is **deleted** and replaced by catalog queries

When saving a routine:
```typescript
// Before
{ name: "Bicep Curl", muscle_group: "Arms" }

// After
{ exercise_id: "abc123", name: "Bicep Curl (Long Bar)", muscle_group: "Arms", equipment: ["LONG_BAR"] }
```

### Analytics & Records

- Primary grouping key: `exercise_id` (joined to catalog for display)
- Fallback for legacy records with NULL `exercise_id`: group by `exercise_name`
- PRs and progress tracked per canonical exercise, not per name string

### New Query Hook

```typescript
function useExerciseCatalog(filters?: {
  muscleGroup?: string;
  equipment?: string[];
  search?: string;
  includeArchived?: boolean;
}) {
  return useQuery({
    queryKey: queryKeys.exercises.catalog(filters),
    queryFn: () => supabase
      .from('exercise_catalog')
      .select('*')
      .eq('archived', false)
      .order('popularity', { ascending: false }),
    staleTime: 1000 * 60 * 30,
  });
}
```

}

## 5. Rollout Order (Portal Side)

```
Step 1: Supabase migration — exercise_catalog table + FK columns (nullable)
   Portal and mobile still work — new columns are nullable, catalog exists but isn't required
Step 2: Seed exercise_catalog from exercise_dump.json
   Catalog populated, nothing references it yet
Step 3: Backfill unambiguous exercise_ids in existing rows
   Historical data improved where safe, ambiguous rows left NULL
Step 4: Deploy updated Edge Functions (sync push/pull)
   New syncs carry exercise_id, old mobile versions still work (exerciseId is optional)
Step 5: Deploy Portal UI changes
   Portal uses catalog for exercise selection, reads exercise_id when available
```

After all portal steps are complete, the mobile update (Step 6) can be deployed independently — see companion spec.

### Backward Compatibility

| Scenario | Behavior |
|----------|----------|
| Old mobile + new portal/edge functions | Mobile doesn't send `exercise_id`. Edge function stores NULL. Portal falls back to name. No regression. |
| New mobile + new edge functions | Full exercise_id flow. Bug #404 fixed. |
| Legacy data (no exercise_id) | Name-based display/grouping. Progressively backfilled as user syncs. |
| Custom exercises | Synced to catalog on push. Available in portal picker. Round-trip preserves ID. |

### What We Do NOT Do

- Drop `name`/`exercise_name` columns (they stay as fallbacks)
- Force-migrate ambiguous historical data (leave NULL, let syncs fill in)
- Require `exercise_id` as NOT NULL (graceful degradation)
- Modify the upstream `exercise_dump.json` format

### Success Criteria (Portal Side)

1. Exercise catalog table populated with 1,176+ exercises
2. Edge functions preserve exercise_id through sync round-trip
3. Portal exercise picker shows all exercises with equipment variants
4. Analytics and records group by exercise_id when available
5. Zero data loss for existing records
6. Old mobile versions continue to work without regression
